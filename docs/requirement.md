# 구독 서비스 요구사항 정의서

---

## 1. 개요

본 프로젝트는 **정기 구독 기반 서비스**로, 카드 / 계좌 / 토스페이처럼 **결제 완료 시점이 서로 다른 결제 수단**을
일관된 구독 상태 관리로 수렴시키는 것을 목표로 한다.

- 결제는 "돈 처리"가 아닌 **상태 전이 트리거**로 취급한다.
- 구독 상태는 **단일 진실 소스(Single Source of Truth)** 이다.

---

## 2. 계정(Account) 도메인 요구사항

### 2.1 회원가입
- 사용자는 다음 방식으로 회원가입할 수 있다.
  - 로컬 계정 (이메일 + 비밀번호)
  - 구글 OAuth
- 비밀번호는 **단방향 해시(bcrypt)** 방식으로 저장한다.

### 2.2 구글 OAuth 정책
- 구글 OAuth 인증 성공 ≠ 로그인
- 최초 구글 인증 성공 시:
  - 계정이 없으면 회원 레코드 생성
  - 계정 상태는 `REGISTERED`
  - **로그인 세션은 생성하지 않는다**

### 2.3 로그인
- 인증 방식은 **세션 기반 로그인**이다.
- 로그인 허용 조건:
  - 계정 상태가 `ACTIVE` 인 경우만 가능

로그인 실패 케이스:
1. 계정이 존재하지 않음
2. 비밀번호 불일치
3. 계정 상태가 `REGISTERED` (가입 미완료)

---

## 3. 구독(Subscription) 도메인 요구사항

### 3.1 구독 상태 정의

| 상태 | 설명 |
|---|---|
| NONE | 미구독 |
| ACTIVE | 정상 구독 |
| EXPIRED | 결제 실패/만료로 구독 종료 |
| CANCELED | 사용자 해지 |

- 사용자당 **동시에 하나의 활성 구독만 허용**한다.

### 3.2 구독 신청/성립 기준
- 사용자가 구독을 신청하면 결제 시도(PaymentAttempt)를 생성한다.
- **결제 성공 이벤트가 확인되는 시점에만 구독을 ACTIVE로 성립**시킨다.
- 결제 실패/만료 시:
  - 신규 신청: 구독은 성립하지 않는다(NONE 유지)
  - 기존 구독 갱신: 구독은 EXPIRED로 전환한다
- 결제 시도가 PENDING인 동안은 해당 사용자에 대해 신규 구독 신청을 허용하지 않는다. (진행중 결제시도 기준)

---

## 4. 결제(Payment) 도메인 요구사항

### 4.1 결제 수단
- 카드
- 계좌
- 토스페이

### 4.2 결제 시도(PaymentAttempt)
- 결제는 "결과"가 아닌 **시도 단위**로 관리한다.

결제 시도 상태:
- `PENDING`
- `SUCCEEDED`
- `FAILED`
- `EXPIRED`

### 4.3 결제 수단별 처리 정책

#### 카드 / 토스페이
- 결제 요청 시점에 즉시 성공 또는 실패 결정
- 실패 시 처리:
  - 신규 신청: 구독 미성립
  - 갱신 결제: 구독 `EXPIRED`

#### 계좌
- 결제 시도 생성 시 상태는 `PENDING`
- **입금 성공 이벤트 발생 시** `SUCCEEDED` 처리
- 입금 이벤트가 없고 만료 시간이 지나면 `EXPIRED`

> **설계 결정**  
> 계좌 결제는 "입금 이벤트를 수동 주입"하는 방식으로 시뮬레이션한다.

---

## 5. 결제 이벤트 처리

- 모든 결제 결과는 **이벤트 기반**으로 처리한다.
- 이벤트는 반드시 **멱등성**을 보장해야 한다.
- 동일 이벤트 중복 처리 시 구독 상태는 한 번만 전이된다.
- 결제 이벤트는 (paymentAttemptId, eventType) 기준으로 멱등 처리한다.

---

## 6. 동시성 및 중복 처리 정책

### 6.1 동시 구독 신청
- 하나의 사용자에 대해 여러 활성 구독은 허용하지 않는다.
- DB 레벨에서 userId + (ACTIVE 구독) 기준 유니크 제약으로 강제한다. (진행중 결제는 PaymentAttempt의 PENDING으로 차단)

### 6.2 결제 중복 시도
- `PENDING` 상태의 결제 시도가 존재하는 경우:
  - 기본 정책: 다른 결제 시도 차단
  - 기존 시도 취소 후 재시도만 허용
- 재시도를 위해 기존 PENDING 결제 시도는 삭제하지 않고 종료(실패) 처리한다. (예: FAILED)

---

## 7. 구독 해지

- 사용자는 언제든지 구독 해지를 요청할 수 있다.
- 해지 시:
  - 구독 상태는 `CANCELED`
  - 즉시 서비스 접근을 차단한다.
- 결제 이력은 유지한다.

---

## 8. 자동 처리 (배치 / 스케줄러)

### 8.1 정기 결제일 처리
- 결제일 도래 시 결제 시도를 생성한다.
- 카드 / 토스페이: 즉시 처리
- 계좌: `PENDING` 상태 유지
- 정기 결제일 산정 방식은 추후 확정한다. (정책 미정)
- 다만 배치 처리의 기준 시점은 "결제일 00:00"으로 고정하고, 결제일 계산 로직만 정책에 따라 교체 가능해야 한다.

### 8.2 결제 실패/만료 처리
- 갱신 결제가 `FAILED` 또는 `EXPIRED`가 되면 구독은 `EXPIRED`로 전환한다.

---

## 9. 알림 및 상태 전달

### 9.1 알림
- 결제 실패
- 결제 만료(미입금 만료 등)
- 구독 만료

> 알림 실패는 시스템 정합성에 영향을 주지 않는다.

### 9.2 실시간 상태 전달
- 구독 상태 변경 시 SSE 기반 전달 가능
- 실시간 전달은 보조 수단이며  
  **최종 상태의 기준은 DB**다.

---

## 10. 게시판(Board) 기능 요구사항

- 게시글 작성자는 세션에서 사용자 ID를 추출한다.
- 게시판 접근 권한은 다음 상태에서만 허용한다.
  - `ACTIVE`
- 구독은 요금제(Plan)를 가진다. (예: BASIC, PREMIUM)
- 프리미엄 게시판은 구독 상태가 `ACTIVE`이고 요금제가 `PREMIUM`인 사용자만 접근할 수 있다.

---

## 11. 범위 제외 사항

다음 항목은 본 프로젝트 범위에서 제외한다.

- 실제 결제 PG 연동
- 가상계좌 발급 및 관리
- 은행 코드 검증
- 정산 / 환불 시스템
- 잔액 및 원장 관리

## 12. 체크 리스트

### ✅ A. 계정 / 인증
- [ ] 프리뷰(공개) 콘텐츠는 비로그인 접근 허용
- [ ] 결제/구독 행위는 로그인 필수
- [ ] 인증 방식은 세션 로그인으로 통일
- [ ] 로그인 상태에서 구독 상태 조회 가능 (Subscription)
- [ ] 로그인 상태에서 결제 이력/시도 조회 가능 (PaymentAttempt/PaymentEvent)
- [ ] 로그아웃 시 세션 무효화 → 프리미엄 접근 즉시 차단

### ✅ B. 결제 수단별 처리 모델

#### 카드/토스페이(즉시 확정)
- [ ] 결제 시도 생성: PaymentAttempt(PENDING)
- [ ] 즉시 결과 이벤트 처리
  - [ ] 성공: PaymentAttempt=SUCCEEDED → Subscription=ACTIVE
  - [ ] 실패: PaymentAttempt=FAILED → 신규는 Subscription 변화 없음, 갱신은 EXPIRED

#### 계좌(비동기 확정)
- [ ] 결제 시도 생성: PaymentAttempt(PENDING, expiresAt)
- [ ] 입금 이벤트 주입 시
  - [ ] PaymentAttempt=SUCCEEDED → Subscription=ACTIVE
- [ ] 기한 초과 시
  - [ ] PaymentAttempt=EXPIRED → 신규는 Subscription 변화 없음, 갱신은 EXPIRED
- [ ] Subscription에 PENDING 상태를 두지 않는다
- [ ] “진행 중” 여부는 PaymentAttempt(PENDING) 존재로 판단한다

### ✅ C. 동시 구독 시도 방지(중복 결제)
- [ ] Subscription이 ACTIVE면 신규 구독 신청 차단(409 또는 멱등 No-op)
- [ ] userId 기준 PENDING PaymentAttempt 존재 시 신규 결제 시도 차단
- [ ] 카드+계좌 동시 시도도 동일하게 차단(동시성 제어)
- [ ] DB 제약: userId 기준 PENDING 1개만 존재(조건부 유니크/동등 방식)
- [ ] DB 제약: userId 기준 ACTIVE Subscription 1개만 존재(조건부 유니크/동등 방식)

### ✅ D. 상태 모델(핵심)

#### Subscription(SSOT)
- [ ] NONE / ACTIVE / EXPIRED / CANCELED

#### PaymentAttempt(진행/결과)
- [ ] PENDING / SUCCEEDED / FAILED / EXPIRED
- [ ] SUCCEEDED/FAILED/EXPIRED는 terminal(종료) 상태로 불변

### ✅ E. 구독 유지 / 해지
- [ ] 사용자 해지: Subscription=CANCELED, 즉시 접근 차단
- [ ] 갱신 결제 실패/만료: Subscription=EXPIRED
- [ ] 정기 결제일 산정은 정책 미정(교체 가능)
- [ ] 배치 기준 시점은 결제일 00:00 고정(계산 로직만 교체)

### ✅ F. 접근 제어(콘텐츠)
- [ ] 프리미엄 접근 조건: Subscription.state == ACTIVE
- [ ] 프리미엄 추가 조건: Subscription.plan == PREMIUM
- [ ] 프리뷰/공개 콘텐츠는 로그인 불필요
- [ ] 접근 제어는 서버에서 수행(프론트 신뢰 금지)

### ✅ G. 이벤트/멱등성(정합성)
- [ ] 결제 이벤트 멱등키: (paymentAttemptId, eventType) 유니크
- [ ] 동일 이벤트 중복 수신 시 상태 전이 1회만 발생
- [ ] 지연/역순 이벤트가 terminal 상태를 덮어쓰지 못하게 한다

### ✅ H. Audit/소프트딜리트
- [ ] 전 엔티티 created_at/updated_at/deleted_at 포함
- [ ] 조회/권한 판단 시 deleted_at IS NULL 기준 적용

---

## 13. 요약

본 시스템은 결제 수단 차이를 **이벤트 타이밍 차이**로 추상화하고,  
구독 상태를 단일 진실 소스로 유지하여 정합성을 일관되게 보장하는 것을 목표로 한다.
